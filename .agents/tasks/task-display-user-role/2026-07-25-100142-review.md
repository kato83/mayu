# Role badge in sidebar user info

A small template addition renders the authenticated user's role as a colored pill badge in the sidebar, between the email line and the logout button. Admin gets an emerald pill, viewer gets blue. The badge is gated behind the existing `authMode !== 'none' && currentUser()` check, so it inherits the auth-mode visibility logic. i18n is handled with custom IDs (`@@sidebar.roleAdmin`, `@@sidebar.roleViewer`) and Japanese translations are provided.

**Watch for:** No fallback rendering for unexpected role values (confirmed) — if the backend ever returns a role other than `admin` or `viewer`, the badge silently disappears. No unit test coverage for the new template branch (confirmed).

## High-level view

The implementation reads `currentUser()!.role` and branches on exact string matches against an untyped field (`role: string` in the `User` interface). The template silently renders nothing for role values it doesn't recognize. Today the backend validates strictly to `admin`/`viewer`, so this is a low-risk gap, but the TypeScript layer offers no compile-time protection if a third role appears.

The sidebar component has no test file. The role badge adds a conditional branch that is exercised only in a running app — there's no spec asserting the badge appears for an admin user or disappears when auth mode is `none`.

The `messages.xlf` diff is large but mechanically generated — the substantive new content is two `<trans-unit>` entries. The rest is line-number shifts and reordering from the extraction tool.

## Role rendering and type safety

The `User` interface declares `role: string`, a wide type. The template performs two exact comparisons:

```html
@if (authService.currentUser()!.role === 'admin') { ... }
@else if (authService.currentUser()!.role === 'viewer') { ... }
```

If `role` holds any other value, the `<div class="mt-1">` wrapper renders as an empty container (no visual artifact, but no badge either). The backend (`internal/auth/auth.go`) defines only `RoleAdmin = "admin"` and `RoleViewer = "viewer"`, and the CLI's `user create` command validates against these. So today this cannot happen through normal paths. The concern is forward-compatibility: adding a third role requires remembering to update the template, and nothing in the type system surfaces the omission.

Narrowing the interface to `role: 'admin' | 'viewer'` would turn a silent rendering gap into a compile error.
