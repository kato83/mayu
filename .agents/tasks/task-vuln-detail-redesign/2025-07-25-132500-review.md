# Vulnerability detail page redesign with CVSS computation and source tabs

The change restructures the vulnerability detail page into a two-zone layout: a merged top section showing the highest CVSS score, risk indicators (EPSS, KEV, LEV), and affected packages aggregated from all sources, and a bottom section with per-source tabs (OSV, NVD, MITRE) for drilling into raw data. On the backend, a new `cvss.BaseSeverity()` function and score-computation logic fills in missing `base_score`/`base_severity` for OSV severity entries and MITRE metrics that only have vector strings in the database. i18n extraction and Japanese translations round out the feature.

**Watch for:** MITRE `BaseScore` is a bare `float64` (not a pointer), so the backend's `m.BaseScore == 0` check cannot distinguish "score genuinely is 0.0" from "score was not provided" — a legitimate NONE-severity vector would not trigger recomputation but also would not have its severity label filled in if both fields happen to be zero/empty (confirmed). The frontend's NVD score collection has no null-guard, meaning a zero-score NVD metric always appears in the merged CVSS list even when it may represent missing data (confirmed).

## High-level view

The backend computation iterates severity entries, parses the vector, and writes back the score and label. The severity threshold logic properly separates CVSS v2 (no CRITICAL level) from v3/v4. The gap is in the MITRE path where `float64` zero-value ambiguity means a metric with `base_score = NULL` in the DB scans to 0.0, triggering recomputation — which happens to produce the correct result for genuinely-zero vectors, but conflates "unknown" with "zero" at the type level.

The frontend `allCvssScores` computed signal collects scores from three source paths with different null-check strategies: `sev.base_score != null` for OSV, no guard for NVD, `m.base_score != null` for MITRE. This asymmetry means NVD metrics always contribute to the merged score list regardless of value.

Tab visibility is driven by presence checks. If a vulnerability has an NVD entry with only a status field and no metrics/descriptions, the NVD tab will appear but show minimal content — an empty-feeling tab that could confuse users.

## CVSS score computation via vector parsing

In `store/detail.go`, the OSV severity loop unconditionally overwrites the computed fields:

```go
for i := range detail.Severity {
    if detail.Severity[i].Score != "" {
        if score, ok := cvss.BaseScore(detail.Severity[i].Score); ok {
            detail.Severity[i].BaseScore = &score
            detail.Severity[i].BaseSeverity = cvss.BaseSeverity(score, detail.Severity[i].Score)
        }
    }
}
```

This is always-recompute rather than compute-if-missing. The `Severity` struct previously had no score/severity fields, so today this is harmless. But it establishes a precedent: if a future OSV entry ships with a pre-computed score that differs from what `go-cvss` calculates, the local computation silently overwrites it.

The MITRE path uses a different strategy:

```go
if m.BaseScore == 0 {
    if score, ok := cvss.BaseScore(m.VectorString); ok {
        m.BaseScore = score
    }
}
if m.BaseSeverity == "" {
    m.BaseSeverity = cvss.BaseSeverity(m.BaseScore, m.VectorString)
}
```

`BaseScore` is `float64`, not `*float64`. A DB row with `base_score IS NULL` scans to `sql.NullFloat64{Valid: false, Float64: 0}` and is assigned as `baseScore.Float64` → 0.0. A DB row with `base_score = 0.0` (legitimate for a NONE-severity vector) also becomes 0.0. In both cases the recomputation fires. The zero-value ambiguity doesn't produce wrong results today because a genuinely-zero-score vector will recompute to zero, and `BaseSeverity(0, vector)` always returns "NONE". But the type conflates "unknown" with "zero", which is a latent correctness issue if the logic ever needs to distinguish the two cases.

## Frontend merged-score asymmetry

The `allCvssScores` signal collects entries from three paths with inconsistent guards:

- OSV: `if (sev.base_score != null)` — skips entries where the backend couldn't parse the vector
- NVD: unconditional push — every metric enters the list
- MITRE: `if (m.base_score != null)` — skips null entries

The NVD path has no guard because `NVDMetricDetail.base_score` is always populated by the NVD API. This is an implicit contract with the backend. If the store ever produces an NVD metric row with a zero/null score, it would appear in the merged list as "0.0 / NONE" and could become the sole entry if no other sources have data — showing a misleading severity badge in the header.

## OSV-only tab redundancy

If the OSV tab is available but has *only* severity entries (no details, no references, no credits), the tab panel will show only the severity rows — which are already visible in the merged CVSS card above. The user sees the same CVSS data twice with no additional context. Consider suppressing severity from the OSV tab when it's already represented in the merged section, or adjusting the tab-availability check to exclude severity-only cases.

## Test coverage gaps

Not tested: the `getEventPairs` helper (range event pairing logic), `getEpssScoreClasses`/`getLevScoreClasses` thresholds, the auto-tab-selection fallback when active tab becomes unavailable, and the specific content of risk indicators (EPSS, KEV, LEV cards). The Go side has thorough boundary-value tests for `BaseSeverity` but no integration test for the `buildBaseDetail` or `fetchMITREMetrics` computation paths (those would require a DB).
