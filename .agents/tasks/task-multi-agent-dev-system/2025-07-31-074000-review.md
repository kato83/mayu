# Multi-agent AI development system for mayu (v2)

This is a second-pass review after all five issues from v1 were addressed in commit `53df67e`. The fixes include: moving `github.event.comment.body` to an `env:` block, correcting the agent name in `agents.md`, adding validation against a known agent list, using first-line routing for multiline safety, and documenting the non-comment trigger path. All five are verified complete. Two new low-severity concerns emerge from the fix implementation itself.

Watch for: The heredoc delimiter `EOF` used for the `instruction` output can be spoofed by a comment body containing a line that is literally `EOF` (**likely** — standard GitHub Actions heredoc vulnerability pattern).

**Verdict**: APPROVED

## High-level view

The script injection fix is correctly implemented. The comment body flows through `env:` into a shell variable, never interpolated into the script source. First-line routing means multiline comments don't break the grep/sed logic. The agent validation step is a simple `grep -qw` against a hardcoded list — functional and readable, with a clear error message on mismatch.

The heredoc delimiter choice (`EOF`) is the only new attack surface. A crafted comment containing a line that reads exactly `EOF` would prematurely close the `GITHUB_OUTPUT` heredoc, allowing subsequent lines to inject arbitrary output variables. The practical exploitability is low because the attacker would need to know this delimiter and craft content precisely, and the validated agent name is the only sensitive output. Switching to a unique delimiter (e.g., `KIRO_INSTRUCTION_END`) would eliminate the vector entirely.

## Heredoc delimiter in GITHUB_OUTPUT

Lines 79-81 of `kiro.yml`:

```bash
echo "instruction<<EOF" >> "$GITHUB_OUTPUT"
echo "$INSTRUCTION" >> "$GITHUB_OUTPUT"
echo "EOF" >> "$GITHUB_OUTPUT"
```

GitHub Actions' multiline output mechanism uses a heredoc-style protocol: everything between `<<DELIMITER` and a line matching `DELIMITER` becomes the output value. If `$INSTRUCTION` (derived from the comment body) contains a line that is exactly `EOF`, the output terminates early, and any subsequent lines become new key=value pairs written to `GITHUB_OUTPUT`.

The validated agent name (`$AGENT_NAME`) is written before the instruction, so the agent routing itself can't be hijacked this way. However, an attacker could inject arbitrary additional step outputs by crafting content after the fake `EOF` line. Whether those extra outputs are consumed by downstream steps is currently "no" (the workflow only reads `agent`, `instruction`, and `routed`), but it's a latent vulnerability if the workflow evolves.

The fix is trivial — use a delimiter that won't appear in natural text:

```bash
echo "instruction<<KIRO_INSTRUCTION_END" >> "$GITHUB_OUTPUT"
echo "$INSTRUCTION" >> "$GITHUB_OUTPUT"
echo "KIRO_INSTRUCTION_END" >> "$GITHUB_OUTPUT"
```
