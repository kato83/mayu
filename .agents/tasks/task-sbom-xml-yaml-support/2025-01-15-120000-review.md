# XML and YAML parsing for CycloneDX and SPDX SBOMs

The SBOM parser, previously limited to JSON, now accepts XML and YAML encodings for both CycloneDX and SPDX formats. The approach extends `detectFormat()` with a three-stage probe (XML prefix → JSON unmarshal → YAML unmarshal), adds separate XML struct types for each format (since Go's `encoding/xml` tags differ from JSON/YAML), and refactors the component-building logic into shared `buildCycloneDXSBOM`/`buildSPDXSBOM` helpers so that all three encoding paths converge on identical normalization. The dispatch table in `Parse()` now handles six format+encoding combinations.

**Watch for:** XML format detection relies on string substring matching (`strings.Contains`) rather than actual XML parsing, which can misclassify documents containing those substrings in unexpected positions (confirmed). The YAML probe will successfully unmarshal any valid JSON, creating ambiguity in detection ordering that the code handles correctly only by trying JSON first (confirmed). SPDX XML struct assumes a specific element nesting (`packages>Package`, `externalRefs>ExternalRef`) that may not match all SPDX XML tool outputs (likely).

## High-level view

Format detection uses a heuristic cascade: check for a leading `<` to detect XML, then try JSON unmarshal, then try YAML unmarshal. Since YAML is a superset of JSON, the ordering is load-bearing — JSON must be tried first or all JSON documents would be classified as YAML. The XML branch uses `strings.Contains` on the full document body rather than parsing a partial XML tree, which is fast but fragile against adversarial or unexpected inputs.

The parsing layer introduces parallel XML struct types for both CycloneDX and SPDX because Go's XML tags (attributes vs. elements, nesting with `>`) are incompatible with JSON/YAML tags on the same struct. XML structural assumptions (element names, nesting paths) are baked into Go tags with no fallback if a tool produces a different layout.

The SPDX XML struct uses `xml:"packages>Package"` and `xml:"externalRefs>ExternalRef"` as its nesting paths. There is no canonical SPDX XML schema mandating these exact element names — different SPDX tools may produce different capitalizations or nesting. The CycloneDX XML struct is on firmer ground since the CycloneDX schema is well-defined.

Tests validate dev detection, no-purl skipping, and empty-component handling for all encodings using inline mock data, but do not exercise malformed input resilience or edge-case XML (namespaced prefixes, CDATA, BOM markers).

## XML detection heuristics in `detectXMLFormat`

The function converts the entire byte slice to a string and searches for substrings:

```go
if strings.Contains(content, "cyclonedx.org") || strings.Contains(content, "<bom") {
    return &detectedFormat{format: FormatCycloneDX, encoding: encodingXML}, nil
}
if strings.Contains(content, "spdx.org") || strings.Contains(content, "<spdxVersion") || strings.Contains(content, "<Document") {
    return &detectedFormat{format: FormatSPDX, encoding: encodingXML}, nil
}
```

The `<bom` check is the weakest link. Any XML document containing an element or attribute name that starts with "bom" (e.g., `<bombardment>`) or that mentions "cyclonedx.org" in a comment would be misclassified and routed to `parseCycloneDXXML`, which would then fail with a confusing `xml.Unmarshal` error. The failure is non-silent, so this is a usability issue (misleading error message) rather than silent data corruption.

A more robust approach would use `xml.NewDecoder` to read the first start element and check its local name and namespace. This avoids scanning the entire document as a string and produces correct results regardless of comments, CDATA, or coincidental substring matches.

## SPDX XML schema assumptions

```go
type spdxXMLDocument struct {
    XMLName     xml.Name         `xml:"Document"`
    SpdxVersion string           `xml:"spdxVersion"`
    Packages    []spdxXMLPackage `xml:"packages>Package"`
}
```

This assumes the root element is `<Document>`, packages live under `<packages><Package>...</Package></packages>`, and external refs nest as `<externalRefs><ExternalRef>...</ExternalRef></externalRefs>`. If a tool produces `<SpdxDocument>` as the root, uses lowercase element names, or places `<Package>` directly under the root without a `<packages>` wrapper, the parser returns zero components with no error — a silent data loss scenario.

Mitigation: after `buildSPDXSBOM` returns, check if the document had content but produced zero components, and surface a warning or error. Alternatively, document that only the "SPDX XML as produced by tool X" subset is supported.

## YAML-JSON detection ordering fragility

Since YAML is a strict superset of JSON, `yaml.Unmarshal` will successfully parse any valid JSON document. The detection code handles this by trying JSON first, which is correct. If this ordering were ever reversed, JSON SBOMs would be misclassified as YAML — still producing correct results but via a slower path. A comment explaining why JSON must precede YAML would prevent future regressions.

## Test coverage gaps

Not tested: malformed inputs (truncated XML, invalid YAML indentation, binary garbage), large documents, XML with namespace prefixes (`<cdx:bom>`), XML with BOM/encoding declarations other than UTF-8, YAML documents with anchors/aliases, or SPDX XML from tools other than the assumed schema. The absence of negative-path tests means regressions in error handling would go undetected.
