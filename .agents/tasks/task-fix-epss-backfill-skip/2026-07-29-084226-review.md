# Align EPSS backfill skip logic with coverage page source of truth

The backfill command skipped dates that had rows in `epss_scores` even when `epss_daily_stats` (the table the coverage page reads) was empty for those dates. This fix changes `GetEPSSImportedDates()` to query `epss_daily_stats` instead of `epss_scores`, adds an orphan-detection query to find the desync, and reconciles it by calling `RefreshEPSSDailyStats` for the affected dates before entering the download loop.

Watch for:
- **Stale comment in context-cancellation path** (confirmed): the inline comment at line 423 still says "reads from epss_scores table directly" — now incorrect.
- **`NOT IN` subquery on large `epss_scores` table** (possible): `GetEPSSOrphanDates` does a `DISTINCT score_date` scan on `epss_scores` within the `BETWEEN` range, which may be slow if the range spans hundreds of days (~200k rows each). Worth verifying the planner uses the `score_date` index for the range filter.

## High-level view

The root cause was a split-brain between two tables: `epss_scores` held the raw data, `epss_daily_stats` drove the coverage UI. A successful row insert into scores followed by a failed `RefreshEPSSDailyStats` left the system in a state where backfill thought the date was imported but the UI disagreed. The fix aligns the skip check with the UI's source of truth and adds a reconciliation step to heal existing inconsistencies.

The reconciliation runs once per backfill invocation, before the download loop. It finds orphan dates (scores present, daily stats absent) within the requested range, calls `RefreshEPSSDailyStats` to rebuild the aggregates, and marks those dates as imported so they aren't re-downloaded. Failures in reconciliation are non-fatal — logged and skipped — so the fix can't make an existing backfill worse.

Tests cover the reconciliation paths (happy, no-orphans, refresh failure, query failure) via a mock store. No integration test exercises the actual SQL against a database.

## Orphan-detection query performance

`GetEPSSOrphanDates` runs:

```sql
SELECT DISTINCT score_date::text
FROM epss_scores
WHERE score_date BETWEEN $1 AND $2
  AND score_date NOT IN (SELECT score_date FROM epss_daily_stats)
ORDER BY score_date
```

The `NOT IN` against `epss_daily_stats` (~900 rows, PK on `score_date`) is cheap. The concern is the outer `DISTINCT score_date` on `epss_scores` — for a full-range backfill (2023-03-07 to today, ~180M rows), the planner may choose a bitmap heap scan rather than an index-only scan on `idx_epss_scores_score_date`. A `LEFT JOIN` rewrite would let the planner start from the small table:

```sql
SELECT DISTINCT es.score_date::text
FROM epss_scores es
LEFT JOIN epss_daily_stats eds ON eds.score_date = es.score_date
WHERE es.score_date BETWEEN $1 AND $2
  AND eds.score_date IS NULL
ORDER BY es.score_date
```

For typical usage (narrow date ranges), the current query is adequate. The concern applies only to full-history backfills.
