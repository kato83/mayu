# EPSS sort option and split sort UI

The change adds `epss_desc` and `epss_asc` sort options across the full stack (API validation, SQL query builder, CLI, TypeScript type union, frontend UI). On the frontend, the monolithic sort `<select>` is replaced with a field dropdown (modified/published/epss) and a direction toggle button, styled with Tailwind and dark mode support.

**Watch for:** Cursor-based pagination silently falls back to `modified_desc` ordering when EPSS sort is active (confirmed). The next-cursor encoding in `server.go` also ignores EPSS, encoding `modified` as the sort key regardless. This means page 2+ of EPSS-sorted results will return incorrectly ordered data.

## High-level view

The cursor-based pagination system has no awareness of EPSS as a sort key. Both the cursor-encoding path in `server.go` and the cursor-decoding/keyset paths in `postgres.go` only recognize "published" and "modified". When a user sorts by EPSS and pages forward, the cursor encodes `modified` as the key, and page 2 reverts to modified-date ordering — producing duplicate or missing results.

The frontend refactor splits sort field from direction cleanly, deriving both from the combined `filters.sort` string by splitting on `_`. The `sortField` getter uses `parts.slice(0, -1).join('_')`, which works for the current single-word fields but would break on multi-underscore field names.

## Cursor pagination breaks on EPSS sort

The `buildOrderClause` function correctly produces `ORDER BY vs.epss_score DESC NULLS LAST, {prefix}id DESC` for `epss_desc`. But cursor-based pagination operates independently from the ORDER BY clause — it applies keyset conditions (the `AND (sort_col < $N ...)` block) to determine which rows have already been seen.

In `server.go` (line ~596), cursor encoding:

```go
sortKey := query.Sort
if strings.HasPrefix(sortKey, "published") {
    nextCursor = store.EncodeCursorWithSort("published", last.Published, last.ID)
} else {
    nextCursor = store.EncodeCursorWithSort("modified", mod, last.ID)
}
```

When `query.Sort` is `"epss_desc"`, this falls into the else branch and encodes `"modified"` as the cursor's sort key. On the next page request, `postgres.go` decodes that cursor, sees `SortKey == "modified"`, and applies keyset conditions on the `modified` column while overriding `sortOrder` to `"modified_desc"`. The ORDER BY from `buildOrderClause` becomes `modified_desc` instead of `epss_desc`.

The result: the first page is correctly sorted by EPSS score, but navigating to page 2 silently switches to modified-date ordering. This will surface as duplicate results, missing results, or visibly reordered rows when paginating.

To fix this properly, the cursor system needs to support EPSS as a sort key. This requires encoding the EPSS score (a float) as the cursor's comparable value and adding keyset conditions on `vs.epss_score` in both `Search` and `searchLight`. The `Cursor` struct currently stores a `*time.Time` for the sort value, so encoding a float requires either a new field or a serialization convention.

Confidence: **confirmed** — traced through both the encoding path in `server.go` and the decoding paths in `postgres.go` lines 735-750 and 1370-1395.

## Untranslatable aria-labels on direction toggle

The direction toggle button uses `[attr.aria-label]="sortDirection === 'desc' ? 'Descending' : 'Ascending'"` with hardcoded English strings. The visible `<span>` elements have proper `i18n` attributes (`@@vulnList.sortDesc`, `@@vulnList.sortAsc`), but the aria-labels lack `i18n-` prefixes and won't be extracted for translation. Screen reader users in non-English locales will hear English labels. Confidence: **confirmed**.
