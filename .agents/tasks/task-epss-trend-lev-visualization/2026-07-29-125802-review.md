# EPSS Trend Graph, LEV Time-Series, and Spike Detection

This change adds three API endpoints (EPSS history with period filter, LEV cumulative history, EPSS trending/spike detection), Angular UI components for visualizing both metrics on the vulnerability detail page and a standalone trending page, plus webhook integration that fires `epss_spike` events after EPSS ingest when CVEs cross a configurable threshold. The architecture is cleanly layered: a `trending` package encapsulates detection logic used by both the API handler and the ingest pipeline, and the frontend follows existing patterns (signals, Chart.js, standalone components, i18n).

**Watch for:** Frontend-backend response shape mismatch on the trending endpoint (confirmed) will cause the trending page and dashboard trending section to render empty. The spike notification goroutine has no error propagation or timeout (confirmed). The trending SQL's `previous_scores` CTE may select the wrong comparison point under certain data conditions (likely).

## High-level view

The backend exposes three new endpoints. `GET /vulnerabilities/{id}/epss-history` gains a `period` query parameter filtering to 30d/90d/365d/all. `GET /vulnerabilities/{id}/lev-history` computes cumulative LEV across the full EPSS time-series then filters the response by period. `GET /epss/trending` compares latest vs N-days-ago EPSS scores, returning CVEs where the delta exceeds a threshold.

The trending SQL uses `DISTINCT ON` with `score_date <= sinceDate` for the "previous" score, intended to find the score closest to N days ago. If there's a gap in ingested data, it may select a score much older than N days, inflating perceived delta. The `LEFT JOIN` also means CVEs with no prior score get `previous_epss = 0`, flagging any CVE with `current_epss >= threshold` as trending even if it always had that score.

The webhook integration fires spike notifications asynchronously after EPSS ingest via a detached goroutine with `context.WithoutCancel`. `FilterNewSpikes` restricts notifications to CVEs in the current ingest cycle, preventing duplicates. The goroutine has no timeout, so a slow DB query or webhook delivery can leak it.

The frontend service expects `{entries: [...], query: {...}}` but the backend returns `{results: [...], days: ..., threshold: ...}`. The frontend `EpssTrendingEntry` also includes a `severity` field that doesn't exist in the backend struct or SQL query. Both the EPSS Trending page and dashboard trending section will render empty.

1. **Trending API response shape mismatch** — Backend returns `{"results": [...], "days": N, "threshold": T}` but frontend `EpssTrendingResponse` expects `{"entries": [...], "query": {...}}`. Fix the frontend interface to match the backend, or add a `map()` operator in the service to transform the response. (confirmed)

Add a join to `vulnerability_summary` for `severity_worst` in the trending query and add the field to the Go struct. (confirmed)
3. **Trending SQL comparison point drift** — `previous_scores` CTE selects `DISTINCT ON (vulnerability_id) ... WHERE score_date <= $1 ORDER BY vulnerability_id, score_date DESC`. If a CVE has no score within the lookback window, it picks the most recent score before that window, which could be months old. This inflates delta for CVEs with sparse history. Consider adding a lower-bound filter or excluding CVEs where `previous_date` is too far from the boundary. (likely)
4. **Spike notification goroutine has no timeout** — `notifyEPSSSpikes` fires `go ing.epssSpikeNotifier(context.WithoutCancel(ctx), ids)` with no deadline. If the store query or webhook dispatch hangs, the goroutine leaks. Add `context.WithTimeout(ctx, 60*time.Second)`. (confirmed)
5. **Missing composite index for trending query** — The trending query scans `epss_scores` with `DISTINCT ON (vulnerability_id) ORDER BY vulnerability_id, score_date DESC`. Without a composite index on `(vulnerability_id, score_date DESC)`, this will be expensive at scale. Not blocking, but worth a migration for production. (possible)

## Trending API contract mismatch

The backend handler at `internal/server/trend.go:137` writes:

```go
writeJSON(w, http.StatusOK, map[string]interface{}{
    "days":      days,
    "threshold": threshold,
    "results":   results,
})
```

The frontend service at `ui/src/app/services/epss-trending.service.ts` declares:

```typescript
export interface EpssTrendingResponse {
  entries: EpssTrendingEntry[];
  query: { days: number; threshold: number; limit: number; };
}
```

`res.entries` will be `undefined` since the JSON key is `"results"`. Both `epss-trending.component.ts` (`this.entries.set(res.entries || [])`) and `dashboard.component.ts` (`this.trendingEntries.set(res.entries || [])`) will always fall through to the empty array.

The frontend `EpssTrendingEntry` interface also includes `severity: string` but `EPSSTrendingEntry` in the Go code has no such field and the SQL in `store/trending.go` does not join `vulnerability_summary`. The trending page's severity column will always render '-'.

## Trending SQL semantics

The `previous_scores` CTE:

```sql
SELECT DISTINCT ON (vulnerability_id)
    vulnerability_id, epss AS previous_epss, score_date AS previous_date
FROM epss_scores
WHERE score_date <= $1
ORDER BY vulnerability_id, score_date DESC
```

`$1` is `sinceDate = now - N days`. If a CVE was first ingested 6 months ago and not seen again until today, `previous_epss` reflects a 6-month-old value, and the delta is attributed to a 7-day window. The `LEFT JOIN` means CVEs with no previous score get `previous_epss = 0`, flagging any CVE with `current_epss >= threshold` as "trending" regardless of how long it's had that score.

A bounded window (e.g., `score_date BETWEEN $1 - interval '3 days' AND $1`) would restrict comparison to CVEs that actually had data near the lookback boundary, eliminating false positives from sparse history.

## Spike notification lifecycle

In `internal/ingest/epss.go`:

```go
go ing.epssSpikeNotifier(context.WithoutCancel(ctx), ids)
```

The goroutine runs detached with no deadline. `detectAndNotifyEPSSSpikes` in `internal/server/ingest.go` calls `trending.DetectSpikes` (a DB query) and then `s.webhookEngine.NotifyEPSSSpikes` (HTTP calls with retries up to 3 attempts each). If the DB is slow or webhooks time out repeatedly, this goroutine blocks indefinitely. A `context.WithTimeout` of 60-120s would bound the worst case without affecting normal operation.

## Test coverage gaps

Not tested: the `notifyEPSSSpikes` goroutine behavior under cancellation or timeout. Not tested: Angular components (`EpssTrendingComponent`, `LevChartComponent`, dashboard trending section) — no unit tests were added for any new frontend code. The API contract mismatch would have been caught by an integration or e2e test exercising the full stack.
