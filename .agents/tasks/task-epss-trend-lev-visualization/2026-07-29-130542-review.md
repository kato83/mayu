# EPSS Trend Graph, LEV Time-Series, and Spike Detection (v2)

This change adds EPSS history with period filtering, LEV cumulative time-series, and EPSS trending/spike detection across three new API endpoints, with corresponding Angular UI (detail page charts with period selectors, standalone trending page, dashboard trending section) and webhook integration for `epss_spike` events post-ingest. The v1 review raised five issues; all have been addressed: response shape now matches (`entries` + `query`), severity populates via `vulnerability_summary` JOIN, the trending SQL uses a bounded window with `INNER JOIN`, and the goroutine carries a 60-second timeout.

**Watch for:** Rapid period-selector clicks fire overlapping HTTP requests with no cancellation of in-flight requests, leading to potential stale-data renders (likely). The LEV history endpoint fetches the full EPSS score history regardless of the requested period, which scales linearly with history length (possible).

**Verdict**: APPROVED

## High-level view

The v1 contract issues are resolved. The bounded window (`score_date BETWEEN sinceDate-3d AND sinceDate`) paired with `INNER JOIN` eliminates both the stale-comparison and zero-previous-score false-positive problems from v1.

The frontend period selectors on the detail page and the standalone trending page both fire HTTP requests on each click without cancelling prior in-flight requests. If a user clicks "30d" then immediately "365d", both requests race and whichever resolves last wins the signal — potentially rendering stale 30d data if the shorter request completes after the longer one.

The LEV history computation always fetches the complete EPSS score history for cumulative accuracy (the since filter is applied post-computation), which is correct mathematically but means the endpoint's DB cost is independent of the selected period.

## Period selector request races

Both `onEpssPeriodChange` and `onLevPeriodChange` call their respective `loadXHistory` methods, which create new subscriptions each time:

```typescript
private loadEPSSHistory(id: string, period?: string): void {
  this.vulnService.getEPSSHistory(id, period)
    .pipe(takeUntilDestroyed(this.destroyRef))
    .subscribe({
      next: (res) => { this.epssHistory.set(res.history || []); },
      ...
    });
}
```

`takeUntilDestroyed` only cancels on component destruction, not on the next call. If a user clicks through periods quickly, multiple in-flight requests race and the last to resolve wins the signal assignment. A longer-period request (365d, fetching more rows) may complete after a shorter one that was initiated later, showing stale data. The `EpssTrendingComponent` has the same pattern in `loadData()`.

The standard fix is a `Subject` piped through `switchMap`, which cancels the prior HTTP request when a new one is emitted.

## LEV history computation cost

`GetLEVHistory` always calls `fetchAllEPSSScores` to retrieve the entire score history, then applies the `since` filter at the application level after computing cumulative LEV for every data point:

```go
// Fetch all historical EPSS scores (need full history for cumulative LEV)
epssScores, err := s.fetchAllEPSSScores(ctx, vulnID)
```

This is mathematically necessary for a correct cumulative value (the LEV at day N depends on all prior days). For a CVE with 365 days of EPSS data, this is ~365 rows — manageable. But if EPSS backfill data spans multiple years, or the retention policy allows unbounded growth, the cost scales linearly with history length on every request.

## Test coverage gaps

Not tested: Angular components have no unit tests (no `.spec.ts` files for `EpssTrendingComponent`, `LevChartComponent`, or the dashboard trending section). The period-selector race condition would be caught by an integration test that simulates rapid clicks.
