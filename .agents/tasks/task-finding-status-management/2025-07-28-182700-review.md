# Manual finding status management for SBOM scan findings (v2)

This change adds a triage workflow for vulnerability findings: users can mark findings as suppressed, false positive, risk accepted, in triage, or resolved. The implementation spans a database migration (two tables with audit log), four new store interface methods with PostgreSQL implementation, two HTTP handlers (PUT to set status, GET to list statuses with filtering), and an Angular UI with status dropdown, justification modal, filter controls, and error feedback.

The three blocking issues from v1 have been addressed: audit log now captures the first status assignment with old_status="open", the UI has an error handler that shows a toast on failure, and the list endpoint validates filter values against the allowed set.

Watch for: Optimistic UI update on status change leaves dropdown showing old value on failure until page reload (**likely**). No rate limiting or idempotency protection on the PUT endpoint (**possible**).

## High-level view

The data model uses `sbom_finding_statuses` keyed on `(version_id, vuln_id, purl)` with an `sbom_finding_status_log` companion for audit. The audit trail is now complete from first triage action, logging the transition from implicit "open" when no prior record exists. Status is scoped to a single SBOM version and does not propagate across version uploads.

The HTTP layer follows the established scan → version → project → user ownership chain for both endpoints. The PUT handler validates status values and enforces justification for `risk_accepted`; the GET handler rejects invalid filter values with 400.

The UI closes the justification modal optimistically before the HTTP response arrives, then shows a localized error toast (auto-dismissing after 5 seconds) if the request fails. The local `findingStatuses` signal map only updates on success, so the dropdown reflects the server state — but the stale selection in the `<select>` element itself may not revert without a re-render triggered by another action.

The current unique constraint prevents duplicate *statuses*, but the log table has no deduplication. ## Dropdown revert behavior on failed status update

The `confirmStatusChange()` method now has an error handler:

```typescript
this.sbomService
  .updateFindingStatus(this.scanId, finding.vuln_id, { ... })
  .subscribe({
    next: (entry) => {
      const map = new Map(this.findingStatuses());
      const key = this.findingKey(finding);
      map.set(key, entry);
      this.findingStatuses.set(map);
    },
    error: () => {
      this.statusUpdateError.set($localize`:@@sbom.scan.statusUpdateError:...`);
      setTimeout(() => this.statusUpdateError.set(null), 5000);
    },
  });
```

The template's `<select>` element uses `[value]="getFindingStatus(finding)"` which reads from the signal map. On error, the map is unchanged, so the *computed* value remains the old status. But the native `<select>` element's DOM state already reflects the user's selection from the `(change)` event. Angular's one-way binding will correct this on the next change detection cycle, but if nothing else triggers CD, the visual mismatch persists. In practice, `statusUpdateError.set(null)` after 5 seconds triggers CD and corrects the dropdown — but during that 5-second window the dropdown shows the wrong value while the error toast is visible. Resetting the signal or forcing the select binding in the error callback would close this gap immediately.
