# Manual finding status management for SBOM scan findings

This change adds a triage workflow for vulnerability findings: users can mark findings as suppressed, false positive, risk accepted, in triage, or resolved. The implementation spans a new database migration (two tables with audit log), four new store interface methods, two HTTP handlers (PUT to set status, GET to list statuses), and an Angular UI that adds a status dropdown per finding row with a justification modal and filter controls.

Watch for: No audit log entry on initial status assignment (**confirmed**). UI has no error handler on the status update call — modal closes immediately regardless of request outcome (**confirmed**). The `ListFindingStatuses` endpoint does not validate filter values, passing arbitrary strings through to the database query (**confirmed**).

## High-level view

The data model introduces `sbom_finding_statuses` keyed on `(version_id, vuln_id, purl)` with an `sbom_finding_status_log` companion table for audit. Status is tracked per-package-per-vulnerability within a single SBOM version and does not propagate across versions — uploading a new version resets all findings to implicit "open".

The backend handlers follow the established ownership verification pattern (scan → version → project → user). The PUT handler validates status values and enforces justification for `risk_accepted`.

The UI defaults to showing only `open` and `in_triage` findings via active filters. Every status change routes through a justification modal (required for `risk_accepted`, optional for others). The `confirmStatusChange` method closes the modal and clears state synchronously, then fires the HTTP request with no error callback — failures are silent.

<details>
<summary>Issues (4)</summary>

1. **No audit log on first status assignment** — The first time a finding's status is set (from implicit "open" to a new value), no audit log entry is created because the lookup for old status returns no rows. Insert a log entry with old_status="open" when no prior record exists, so the audit trail is complete from the first triage action.
2. **UI has no error handling on status update** — `confirmStatusChange()` closes the modal and clears pending state before the HTTP response arrives, and the `subscribe()` call has no `error` callback. If the request fails, the user sees no feedback. Add an error handler that shows a toast or notification on failure.
3. **Status filter values not validated on list endpoint** — `HandleListFindingStatuses` passes the raw comma-split `?status=` values directly to the SQL `ANY($2)` clause without checking they are valid statuses. Invalid values silently return empty results rather than a 400 error. Validate each filter value against the allowed set and return 400 for invalid ones.
4. **`resolved` status ambiguity with scan-level resolution** — The scan already tracks `resolved_findings` at the diff level (findings that disappeared between scans). A user manually marking a finding as `resolved` creates a semantic overlap. Consider documenting the intended semantics or renaming the manual status to `manually_resolved`.

## Audit log gap on initial status assignment

In `postgres.go`, `UpsertFindingStatus` reads the existing status before the upsert:

```go
var oldStatus sql.NullString
err = tx.QueryRowContext(ctx, `
    SELECT status FROM sbom_finding_statuses
    WHERE version_id = $1 AND vuln_id = $2 AND purl = $3`,
    fs.VersionID, fs.VulnID, fs.Purl,
).Scan(&oldStatus)
```

When no row exists, `oldStatus.Valid` is false. The log insertion is gated on `oldStatus.Valid && oldStatus.String != result.Status`, so the very first triage action produces no audit record. Every subsequent change is logged, but the initiating event is lost. This matters for compliance workflows where a complete audit trail from first action is expected.

## Fire-and-forget status updates in the Angular component

```typescript
confirmStatusChange(): void {
    // ...
    this.sbomService
      .updateFindingStatus(this.scanId, finding.vuln_id, { ... })
      .subscribe({
        next: (entry) => {
          // update local map
        },
      });

    this.showJustificationModal.set(false);  // closes immediately
    this.pendingStatusChange = null;
    this.justificationText = '';
}
```

The modal dismissal and state cleanup happen synchronously, outside the subscribe callback. If the network request fails (400, 500, timeout), there is no `error` handler to notify the user. The dropdown reverts visually on the next render (since the map only updates on success), but the user has no indication the save failed. A loading state on the confirm button while in-flight and an error toast would close this gap.

## Unvalidated filter parameter on list endpoint

`HandleListFindingStatuses` splits the `?status=` query param on commas and passes the resulting slice directly to the SQL `ANY($2)` clause. If a caller sends `?status=foo,bar`, PostgreSQL returns no matches silently — no error, no feedback. The PUT handler already validates status via `isValidFindingStatus`; the list handler could reuse the same check per filter value.

## Version-scoped status and cross-version behavior

Finding statuses are keyed on `version_id`, so suppressing CVE-X in version 1.0 has no effect when version 1.1 is uploaded — that finding appears as "open" again. Users with frequent version uploads may need to re-suppress findings repeatedly. The API surface doesn't expose a "copy statuses from previous version" operation, which could be a future enhancement if this becomes a friction point.
